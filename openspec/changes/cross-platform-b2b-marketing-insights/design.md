# Design

## Context

參見 `proposal.md` 的動機與範圍，以及兩份 capability spec 的可觀察行為。來源提案沒有既有程式碼或系統架構可沿用；三平台 API 權限、欄位、更新限制及客戶去重方法尚未確認。CVR、CAC 定義以提案為準：整體 CVR 為三平台總訂單數除以總訪問數；整體 CAC 為三平台廣告總支出除以新增不重複客戶數。這些分子分母的跨平台歸屬與重複計算需在實作前核對。

## Prototype Authorization (2026-11-10)

使用者授權建立僅供展示與互動驗證的 Mock Data 原型，允許採用暫定指標定義。此授權不代表研究負責人已核准 SAP、資料字典、歸因、去重或有效樣本規則，也不代表目標使用者已核准正式建議規則。原型只使用合成資料，不連接任何平台、不輸入客戶資料、不執行預算變更；所有指標、品質狀態及預算建議均須標示為示意。正式探索與研究仍受 Task 1.2、1.4、4.2 及 4.3 關卡限制。

原型暫定欄位：平台、週期、訪問數、訂單數、廣告支出、新客數、同步狀態、最近成功更新時間、完整性/差異/去重品質狀態。分平台 CVR = 訂單數 ÷ 訪問數；分平台 CAC = 廣告支出 ÷ 新客數。跨平台 CVR 僅在平台與期間涵蓋完整且訪問/訂單口徑可比時，以總訂單 ÷ 總訪問示意；跨平台 CAC 因尚無核准的跨平台去重資料，一律顯示不可用，不推估去重客戶數。

## Goals / Non-Goals

**Goals:**
- 定義可替換平台來源的資料匯入與正規化邊界，讓報表不直接依賴各平台原始欄位。
- 使每個指標與預算建議可追溯至期間、來源資料、品質狀態及使用者後續決策。
- 將資料品質判斷與指標呈現分開，避免資料不足時呈現貌似完整的彙總。

**Non-Goals:**
- 自動調整廣告預算或代替使用者登入平台執行操作。
- 在未確認資料或研究設計前，指定建議演算法、統計門檻、API 供應商、雲端架構或成本目標。
- 擴展至提案以外的平台、客群或產業。

## Decisions

1. **平台連接器與共通資料模型分層。** 每個來源先映射至共通的期間、平台、訪問、訂單、支出、新客及來源更新狀態欄位；保留來源識別及原始期間資訊以供追查。選擇此邊界可避免報表邏輯綁定單一平台欄位；替代方案是各平台直接產生報表，但會重複指標邏輯且難以比較。具體欄位映射須先完成 API 可行性確認。

2. **指標計算使用可配置且版本化的定義。** CVR／CAC 的公式與資料期間須有明確版本，API 匯入及報表共用同一計算邏輯。跨平台重複客戶辨識、訂單歸因與各平台定義差異尚待研究治理文件核對；未確認前，系統應標示限制或停止計算，不自行假設能精準去重。

3. **資料狀態伴隨每份報表及建議。** 同步時間、平台涵蓋、缺漏、延遲與差異查核結果是報表的一部分，而非只寫入技術記錄。替代方案是僅在背景記錄錯誤，但無法讓使用者判斷數據是否可供決策。

4. **預算建議與平台執行採分離式流程。** 系統產出建議及理由／資料期間，使用者另外記錄採納狀態與實際調整；本輪不直接串接寫入預算。這符合人工調整及可稽核需求，也降低未驗證建議造成直接支出的風險。建議規則須由研究和產品驗證決定，現階段不指定 AI 或特定模型。

5. **以關卡控制研究放行。** API 與資料可行性、MVP 驗收及研究治理先就緒，再進行 5 家／4 週探索；正式六個月配對隨機研究只在探索及治理條件符合後啟動。CVR 提升 8 個百分點、CAC 相對下降至少 5% 且優於對照組為提案既有成功門檻，統計方法及有效樣本按 SAP，不在此另造。

6. **暗色系原型以獨立頁面提供。** 新增 `prototype/dark.html`，沿用原型的 HTML 結構、`app.js` 與互動，透過頁面主題標記套用 `styles.css` 中的暗色樣式。原本 `prototype/index.html` 保持淺色入口；暗色版涵蓋總覽、建議與歷史等所有既有畫面，不新增主題切換或改變示範資料與行為。`.vscode/mcp.json` 不屬於 prototype 的設定入口，不需修改。

## Risks / Trade-offs

- [平台 API 無法提供等價欄位或權限] → 在建置前逐平台核對 API、授權、限制及成本；不足時縮小可比較範圍並明確揭露，不宣稱全平台涵蓋。
- [平台對訂單、訪問及新客的定義不一致] → 建立欄位對照與指標口徑審查；無法合理轉換時呈現分平台值及不可比較狀態。
- [跨平台客戶重複造成 CAC 偏差] → 核對可用去重資料、隱私限制及 SAP；未達品質條件則不將彙總 CAC 作為成功結論。
- [建議被誤認為自動或保證有效的指令] → 在介面標示建議期間、資料狀態與人工決策責任，僅記錄不執行。
- [小樣本或研究執行偏差] → 探索階段只驗證可行性；正式效果結論須依 SAP、對照組及資料品質審查。
- [成本與付費意願未知] → 在下一關卡前估算 API、建置、維運及單客成本，蒐集付費意願；未有證據前不宣稱投資回收。

## Migration Plan

目前沒有既有產品或使用者資料需要遷移。實作時先完成唯讀 API 可行性與資料映射，再以樣本資料驗證正規化及指標；通過準備關卡後才提供 MVP 試用。若同步或計算結果不可靠，停用受影響來源的彙總與建議，保留狀態及既有調整紀錄供調查；恢復前重新核對資料並依 SAP 確認是否需要重算。部署與回復方式須按最終技術架構補足。

## Open Questions

- 各平台 API 是否能提供所需欄位、歷史期間、更新頻率及商用授權？
- 新增不重複客戶的跨平台識別及歸因口徑為何？哪些平台資料可比較？
- SAP 最新版本對配對、隨機分派、有效樣本及不足資料結論的完整規則為何？
- 建議需呈現哪些可解釋依據，以及資料品質達到何種條件才可產生建議？
- 資料保存期限、個資處理、企業權限模型及 API 憑證管理要求為何？
- 經核實的人力、時程、API 費用、維運成本與商業訂價為何？
